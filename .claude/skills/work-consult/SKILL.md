# Work Consult

## 目的

ユーザー判断が必要なときに使う。
出力は、選択肢、トレードオフ、推奨案、決定事項をまとめた判断材料である。

## 入力

- ユーザー依頼または判断したい論点
- 調査結果
- 既知の制約
- 専門エージェントの意見
- 既存仕様やワークフロールール

## Manager の進め方

1. 必要な判断を具体化する。
2. 事実と仮定を分ける。
3. 判断に影響する場合だけ、専門エージェントに範囲を絞って意見を求める。
4. 選択肢とトレードオフをユーザーに提示する。
5. 根拠が十分なら推奨案を出す。
6. ユーザーの決定または残った不明点を記録する。
7. 調査、計画、実装、終了のどれに進むか決める。
   実装へ直接進めるのは、目的、スコープ、非対象、受け入れ条件、制約がすでに揃っている場合だけとする。

## 専門エージェントの使い方

- `Security`: リスク受容、認証、秘密情報、公開範囲、依存関係の判断。
- `UX Reviewer`: ユーザー向け挙動、文言、フォーム、操作フローの判断。
- `Structure Reviewer`: 所有境界や配置判断。
- `Spec Reviewer`: 仕様と実装の乖離に関する相談のみ。
- `Consistency Reviewer`: 既存パターンとの整合に関するトレードオフがある場合。任意。
- `Developer`: 実現可能性や実装コストの見積もりのみ。read-only / no edits / no implementation。

## 判断境界

相談では推奨はできるが、次はユーザー判断とする。

- スコープまたは非対象の変更。
- 受け入れ条件の変更。
- Security または UX リスクを修正せず受容する判断。
- 仕様上の挙動変更。
- 優先度の変更。

## やること

- 判断論点を明確にする。
- 具体的な選択肢を 2-3 個に絞る。
- 根拠がある場合は推奨案を出す。
- 決定後に何が進むかを明記する。

## やらないこと

- 未解決の仮定を隠さない。
- 専門エージェントの意見をユーザー承認として扱わない。
- 実装を始めない。
- ユーザー承認なしに仕様書を更新しない。
