# Work Design

## 目的

ユーザー依頼を実装可能な設計に変換する。
現行ワークフローの 1-3 を扱い、実装前に止める。

## 入力

- ユーザー依頼
- 調査結果
- 相談で決まった判断
- 既存仕様、ロール定義、制約

## 実装開始に必要な項目

Manager は Developer Request を作る前に、実装判断に必要な認識が User と Developer の間で揃う状態まで計画を具体化する。

次が明確になるまで実装を始めない。

- 目的
- スコープ
- 非対象
- 受け入れ条件
- 制約

## Manager の進め方

1. 目的、スコープ、非対象、受け入れ条件、制約を明確にする。
2. 実装前に Security、UX Reviewer、Developer 実現可能性レビューが必要か判断する。
3. 範囲を絞って事前レビューを依頼する。
4. フィードバックを設計へ反映する。
5. ユーザー判断が必要なら `work-consult` に戻す。
6. `work-implement` へ渡す Developer 依頼を作る。

## 実装前レビューの起動条件

- `Security`: 外部入力、認証、公開機能、秘密情報、外部通信、依存関係。
- `UX Reviewer`: GUI、CLI 文言、通知、フォーム、ユーザー向けフロー。
- `Consistency Reviewer`: 既存プロジェクトへの機能追加・修正の場合。提案アーキテクチャ・パターンが既存コードと整合するか確認する。
- `Developer`: 実現可能性、テスト可能性、実装境界、担当ファイル候補。read-only / no edits / no implementation。

## やること

- 要件をテスト可能な形にする。
- 非対象を明記する。
- レビュー指摘を、設計変更またはユーザー判断に分類する。
- Developer への handoff を具体化する。

## やらないこと

- 実装を始めない。
- 曖昧な要件を実装に流さない。
- コードやコード付随ドキュメントを更新しない。
- 未解決のレビュー指摘を受容済みにしない。

## 差し戻し条件

- 仕様不明。
- テスト不能。
- 設計矛盾がある。
- 重大なセキュリティ懸念がある。
- 重大な UX 懸念がある。
- スコープや受け入れ条件の根本変更が必要。
